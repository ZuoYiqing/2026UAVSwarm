各组各跑一轮，先后顺序是 `min_p=0`，再 `temperature=0.7,min_p=0`，最后关闭服务端 JSON Schema 格式约束。
后两项参考[面壁官方部署说明](https://github.com/OpenBMB/MiniCPM/blob/316cfb1cea39f39cfa16b4f5703b77495c2340be/docs/deployment/llama_cpp.md)；
客户端在结果中记录实际发出的参数。未关闭客户端的本地 JSON/语义校验，不自动修复内容。
一次运行并不足以构成性能排名，输入是自建合成题，运行顺序和提示缓存也可能影响结果。

## 目标语义校验的修复

上一轮 18 题中，旧规则把“北仓只是背景地标；只前往南库”误读成两个目的地，并错误放行。
本轮增加明确的背景/参照角色识别：这些实体仍出现在场景中，但不会自动成为任务目的地；
模型若把它们选中，返回 `NON_TARGET_REGION_SELECTED`。
不认识的背景表达或“既是背景又要求前往”的矛盾会拒绝，并给出需要澄清的原因；
这里尚未接入主线新增的操作员澄清通道。
这是受限的规则处理，不等于通用中文语义理解；未来仍需人工语义审核与更完整契约。

同一冻结题集在**修复后**规则基线为 12/17 候选语义、18/18 接受/拒绝一致、错误放行 0；
修复前的 11/17、错误放行 1 保留在上轮历史报告，不覆盖原始证据。
49/49 算法单元测试、40/40 离线框架案例通过，其中包含背景角色、模型误选和矛盾表达测试。
算法结果仍是候选提案，`execution_authorized=false`。

下一步更有价值的是将输出契约改成能明确表达“未知/需澄清”，增加独立任务分布和人工标注，
再决定是否做小模型领域微调。若仅为了当前的 0/17 多调温度，容易在自建题上过拟合。
