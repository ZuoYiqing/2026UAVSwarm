## 结果

4B Q4模型完成了第一个三机巡检提案。结构化输出是合法JSON，三个task/node/action/waypoint
分配均与权威输入一致，但提案被确定性校验器拒绝，不能进入任何执行链。

拒绝原因只有 `STATUS_REASON_MISMATCH`：模型给出顶层 `status=proposed`，
却错误使用任务级 `reason_code=ASSIGNED`；契约要求 `MISSION_PROPOSED`。
原始失败不自动修复，`accepted_proposal`保持null，CLI以返回码1明确报告失败。

更重要的是，解释中出现“Direct path available”和“All constraints are met”。
输入只含scene_ned位置与预定义航点，没有障碍物、禁飞区、分离、航迹或能源可行性证明。
因此即便只改原因码也不能把原结果当作安全计划。这证明模型适合提出候选，
但几何规划、约束验证和Runtime/Policy复核不能交给语言模型自证。

## 根据失败做的加固

没有增加“模型答错后自动改成正确值”的修复路径。改动作用于下一次原始生成：

- 输出Schema缩小顶层与未分配任务的原因码范围。
- Schema加入status/reason/assignments/unassigned_tasks之间的条件关系。
- 提示词明确三种顶层状态的原因码映射，ASSIGNED只能用于assignment。
- 禁止模型宣称直达/安全路径、障碍物或禁飞区净空、最小间距、碰撞安全、能源或调度安全，
  以及“全部约束已满足”；必须保留未验证限制。
- 新增回归测试，旧错误原因码现在在Schema层即被拒绝。

当前回归：21/21 Python单元测试、40/40框架案例、9/9无网络下载器测试通过。
加固后的模型尚未复跑：继续任务时可用系统内存低于启动门槛5GiB。
下一次模型启动还要验证推理引擎是否完整支持新增Schema条件子集；不兼容应明确失败，
不得退回无约束生成而不标注。
单请求脚本现在默认在请求结束后关闭本次模型服务；只有显式 `-KeepServer` 才保留，
避免在16GiB机器上长期占用内存。

## 当前判断

这台机器足以进行4B量化模型的单请求与小批量实验，不需要为这一阶段租服务器。
批量评测前仍要释放足够RAM、按单请求监控资源，并在每轮后停止模型。
服务器适合后续训练、24/27B对照、多模型并行或大量重复实验，不是修复契约错误的办法。
