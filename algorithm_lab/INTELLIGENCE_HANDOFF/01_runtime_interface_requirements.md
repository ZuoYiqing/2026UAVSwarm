## 0. 先划清边界：哪些不归算法

Algorithm Lab 负责**智能**部分——语义理解、意图形式化、不确定条件下的决策、失效归因、跨域泛化。

以下内容**有确定解、属于传统算法**，明确归 Runtime / 规划负责人，**Algorithm Lab 不实现、不优化、不代为求解**：

| 类别 | 归属 | 说明 |
| --- | --- | --- |
| 航迹几何、禁飞区、障碍物规避 | 路径规划负责人 | 几何可判定问题 |
| 多机安全间隔、冲突解脱 | 路径规划负责人 | 确定性几何约束 |
| 时间窗调度、并发时间表 | Runtime 调度 | 组合优化，有成熟求解器 |
| 能耗预算与返航电量 | Runtime / 机型负责人 | 机型相关物理模型 |
| Policy 授权裁决 | Policy 负责人 | Runtime 已有 Policy Gate |
| 执行与遥测闭环 | Runtime + Adapter | 已有 |

**当前 `algorithm_lab/mission_llm_poc` 的实现是"闭环验证脚手架"**（greedy 分配 + 严格校验器），不是算法成果。它的价值在于冻结 I/O 契约、可复现、可审计。真正的智能算法尚未开始。

## 1. 核心诉求：把"结构化任务清单"的权威来源从输入改为输出

这是**当前架构里最关键的一处语义倒置**，也是后续所有智能能力的前提。

### 现状

`mission_context.schema.json` 的输入里同时包含：

- `objective`（自然语言，`mission_context.schema.json:50-54`）
- `tasks[]`（结构化任务，含 `required_actions` 与 `waypoint_ids`，`mission_context.schema.json:266-315`）

而系统提示词 `prompts/mission_planner_system.txt:8-9` 规定：

> "Tasks and their required_actions/waypoint_ids are authoritative. Copy each assigned task's action sequence and waypoint references exactly; changing the task is not a successful plan."

`docs/ALGORITHM_DELIVERY_REPORT.md:40` 也写明：

> "任意自然语言语义矛盾…不属于已验证能力"

### 后果

在这个契约下，**模型不允许从自然语言生成任务，只允许把已有结构化任务分配给节点**。自然语言目标与结构化任务冲突时，提示词要求模型"拒绝"（`mission_planner_system.txt:18-19`）——即把语义一致性判断推给模型和人工。

于是发生倒置：**自然语言是操作员的原始意图，却被降级为"不可信的附加数据"；而本该由它派生的结构化任务清单，反过来成了权威。**

`README.md:54-55` 对此的表述是：

> "输入必须提供权威 task/action/waypoint 清单。第一版只让模型提出分配并解释，**尚未实现从自然语言自由生成任务图、覆盖路径或坐标**。"

### 需求

请确认并支持以下语义变更方向：

1. **自然语言指令是权威意图来源**；结构化任务清单是**派生结果**（由智能算法生成），不是输入前提。
2. 在正式变更前，需要 Runtime 提供**场景可供性数据**（见第 2 节），使算法具备"把 `objective` 落成具体航点/动作"所需的信息基础。
3. 过渡期内建议双轨：`objective` 与 `tasks[]` 并存时，**明确声明谁是权威**，并对"二者冲突"给出确定性的处理规则（拒绝 / 请求澄清 / 以 objective 为准并标记），而不是依赖模型自行判断。

> **说明**：Algorithm Lab 理解当前设计是为了先冻结契约、保证可复现。本项不是缺陷报告，是**下一阶段的能力解锁前提**。请评估变更窗口。

## 2. 算法侧需要的数据（按优先级）

以下字段**不在当前 schema 中**。Algorithm Lab 需要它们来做语义决策。**若 Runtime 认为应由算法侧从已有数据推导，请明确指出，我方调整。**

### P0 — 阻塞项，缺失则智能能力无法起步

| 数据 | 用途 | 为什么算法要它 |
| --- | --- | --- |
| **任务/区域的自然语言或结构化描述** | 把 `objective` 中的语义指代（如"山谷东侧""上次失联那片区域"）绑定到具体 `region_id` / `waypoint_ids` | 这是"语义锚定"，是智能算法的核心职能。仅靠 ID 无法完成指代消解 |
| **场景实体清单**：障碍物、禁飞区、地形/建筑物范围 | 让算法能**推理**某方案为何不可行，并生成替代方案 | 注意：**几何判定归规划**；算法需要的是"存在什么约束"的语义信息，用于解释与再规划，不是自己算几何 |
| **载具能力语义**：续航、速度包线、传感器视场/分辨率 | 让算法能在**满足任务语义**的前提下做取舍（如"哪台更适合拍这个目标"） | 当前 `capabilities` 只有 6 个动作枚举（`mission_context.schema.json:135-150`），无法区分"能拍"与"拍得清" |

### P1 — 重要，影响决策质量

| 数据 | 用途 |
| --- | --- |
| **失败/异常历史**（含失败原因、当时条件） | 失效归因与经验复用。当前 schema 完全无历史概念，算法无法从"上次这样不行"中学习 |
| **每字段时效**（而非单一 `snapshot_age_ms`） | `ALGORITHM_DELIVERY_REPORT.md:58` 已指出需要"每字段时效"。当前是全局单值，粒度不足 |
| **任务优先级 / 时间窗口 / 截止期** | 语义上的"先做哪个"，与调度的时间窗不同层次 |
| **Policy 拒绝的结构化作用域** | 当前 `policy_denials` 只有 `node_id`/`action`/`reason_code`（`mission_context.schema.json:316-349`），缺"作用域、有效期、可否申诉"。报告 `:59` 要求"节点/动作/任务作用域、拒绝原因及有效期" |

### P2 — 未来能力所需

| 数据 | 用途 |
| --- | --- |
| **链路质量时序**（非单一 `connected` 布尔） | 降级决策与簇首权威判断 |
| **簇结构**（簇首/簇内成员关系） | 三层指控的簇级算法。当前 schema 无簇概念，`fleet` 是扁平列表 |
| **多视角观测/图像引用** | 若后续引入 VLM 类能力，需要观测数据的可达引用 |
| **人类反馈通道**（确认/否决/修正记录） | 上下文学习与自进化闭环的数据来源 |

## 3. 算法侧对 Runtime 的保证（反向承诺）

为避免职责重叠，Algorithm Lab 明确承诺：

1. **算法输出永远是提案**，`execution_authorized` 恒为 `false`，不触碰执行链路。
2. **算法不做几何与调度计算**，几何/调度可行性由 Runtime / 规划侧独立校验，算法输出必须能被其否决。
3. **算法不重新裁决 Policy**，`policy_denials` 视为硬约束。
4. **算法不访问飞控、不发送 MAVLink、不操作 payload。**
5. **算法输出满足冻结的 JSON Schema**，并附输入/提示词/输出哈希、模型标识、推理设置，支持审计与 replay。
6. **算法不延长快照 TTL** 来掩盖陈旧状态；快照过期时重新校验或重新规划。

## 4. 需要 Runtime 负责人确认的四个问题

1. **权威来源**：`objective` 与 `tasks[]` 并存时，谁权威？冲突如何处理？变更窗口如何安排？
2. **数据供给**：第 2 节 P0 字段由 Runtime 提供，还是认为应由算法侧从现有数据推导？
3. **职责确认**：第 0 节表格中的归属划分是否与 Runtime 理解一致？有无遗漏或重叠？
4. **接入方式**：算法提案进入主线的路径是 schema 映射 + 人工确认（`ALGORITHM_DELIVERY_REPORT.md:61`）还是其他？快照过期后的重新验证由谁负责？

## 5. 当前不需要 Runtime 做的事

明确列出，避免误解：

- **不需要**为算法实现几何求解器或调度器（那是规划/调度的职责）。
- **不需要**为模型腾出显存或改变部署方式（选型由算法侧负责）。
- **不需要**修改 Policy Gate 的现有裁决逻辑。
- **不需要**接入任何真实飞控来配合算法实验（算法实验使用合成 fixture，已标注 `synthetic_benchmark`）。
