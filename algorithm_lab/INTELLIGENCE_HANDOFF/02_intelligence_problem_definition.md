# Algorithm Lab 问题定义：无人机三层指控中的智能算法

**版本**：v0.1
**日期**：2026-09-24
**性质**：Algorithm Lab 的职责声明与问题定义。用于界定"智能算法"的范围，避免与 Runtime / 规划 / 调度职责混淆。

---

## 0. 判据：什么算智能问题

**判据只有一条：状态空间是否可穷举。**

| | 状态空间 | 归属 | 处理方式 |
| --- | --- | --- | --- |
| **可穷举** | 有限、可枚举 | 传统工程 | 查表、规则、求解器。**不需要智能，也不要上模型** |
| **不可穷举** | 开放、组合爆炸、需语义理解 | **Algorithm Lab** | 学习/推理/泛化 |

这个判据的直接后果，是一个**反直觉但重要**的结论：

> **失联（link lost）时的动作选择，不是智能问题。**

理由：`src/uav_runtime/policy/fallback_actions.py:34-38` 已把失联动作限定为有限的确定性白名单（`hold_position`、`return_home`、`land_safe`、`reduce_speed`、`maintain_heading` 等）。**在有限集合内做选择，用确定性规则表即可，且必须用规则表**——因为失联时无人可复核，可预测性优先于最优性。

**过去几轮讨论中，把这件事当成"要放个小模型来做决策"是错的。** 本文件明确纠正这一点。

同理，以下**都不是**智能问题：航迹几何、禁飞区判定、多机安全间隔、时间窗调度、能耗预算、Policy 裁决。这些都有确定解，归对应负责人。

## 1. 五个真正的智能问题

### 问题 A：语义锚定 —— 把不精确的自然语言意图落成可执行参数

**这是最核心的问题，也是整个系统"智能"与否的分水岭。**

**问题陈述**：操作员说"扫描山谷东侧那栋楼，重点看北面"。系统必须输出：哪个 `region_id`、哪几个 `waypoint_id`、什么高度、什么传感器指向、覆盖顺序。

**为什么难**：
- "东侧""北面"是**相对参照系**表述，需结合任务上下文与场景知识消解
- "重点"是**优先级与分辨率**的语义，不是坐标
- 指代可能依赖历史（"上次失联那片"）或常识（"那栋楼"）
- **必须拒绝发明**：`mission_planner_system.txt:6` 要求"Do not invent coordinates"，但现有 schema 里没有任何可供锚定的场景语义数据

**为什么不可穷举**：自然语言指令的表述空间是开放的。同一个意图有无限种说法，同一句话在不同场景下含义不同。

**现状**：完全未实现。当前输入强制自带权威 `tasks[]`，模型只做分配（`README.md:54-55`、`DELIVERY_REPORT.md:40`）。

**依赖**：Runtime 提供场景可供性数据（见 `01_runtime_interface_requirements.md` 第 2 节 P0）。

---

### 问题 B：欠信息决策 —— 数据缺失/陈旧/冲突时怎么决策

**问题陈述**：`battery_pct` 为 `null`、`stale=true`、`public_position_usable=false`、快照即将过期时，系统该怎么决策？

**为什么是智能问题**：现有校验器把这些一律**硬拒**——`semantic_validator.py:46-63` 里 `NODE_OFFLINE`、`TELEMETRY_STALE`、`BATTERY_UNKNOWN`、`SPATIAL_UNAVAILABLE` 全部直接判该节点不合格。

这是**保守但僵化**的：真实战场大量时间处于"部分信息"状态，一律拒绝等于放弃任务。但盲目乐观更危险。

**真正的问题是**：如何**量化不确定性并做出风险相称的决策**——比如"电量未知但有 70% 把握够用"是否可接受，取决于任务的风险等级、可撤退性、以及是否有替补节点。这是**风险敏感决策**，不是布尔过滤。

**为什么不可穷举**：缺失字段的组合、缺失程度、任务上下文的组合是开放的。

**现状**：`test_lab.py` 有相关案例（`low_battery`、`uav02_offline`、`missing_goto`），但判据是"是否拒绝"，不是"决策质量"。

---

### 问题 C：失效归因与策略调整 —— 计划失败之后做什么

**问题陈述**：任务执行到一半,某节点掉线/超时/任务未达成。系统需要回答:**为什么失败**（节点故障？指令歧义？环境变化？约束本身矛盾？），以及**该重试、换方案、还是放弃**。

**为什么是智能问题**：
- **归因需要因果推理**，不是模式匹配——同样的"超时"可能是通信问题、可能是航程估计错误、可能是指令本身不可行
- **策略选择依赖归因结果**：归因错了,重试就是浪费
- 当前 schema **完全没有历史概念**,算法无从"从上次失败中学习"

**可借鉴**：清华 Zeva 的 In-Context Causal Learning（迁移"动作—状态变化"的因果关系而非任务经验,零梯度更新）；中科大 ADRS 对长链路的时间信用分配。

**为什么不可穷举**：失败模式开放,且组合出现。

---

### 问题 D：多机协同的语义层 —— 不是几何避碰

**问题陈述**：多机之间需要协商的是**语义层**的事：
- 任务分工是否互补,还是重复覆盖？（两架都去拍同一面墙）
- 视角是否互补？（需要多角度重建时的站位语义）
- 通信中继角色由谁承担更合理？
- **簇首失效时,簇的语义角色如何重新分配？**

**为什么是智能问题,且必须与几何分开**：
- **几何避碰**（航迹间距、冲突解脱）是确定性问题 → 归规划负责人
- **语义协同**（谁该做什么角色、覆盖是否冗余、视角是否互补）**没有唯一正确答案**,依赖任务意图与环境语义 → Algorithm Lab

把这两件事混在一起,是当前架构最容易被误解的地方。**我们不碰几何。**

**可借鉴**：HERON-World Model 的多智能体交互预测（预判动作相互影响）,但注意其算力需求,机载部署需实测。

---

### 问题 E：泛化与持续适应 —— 换场景、换机型、越用越准

**问题陈述**：三层指控的三层（地面显控 / 簇首 / 簇内节点）硬件不同、视角不同、可用算力不同。同一套智能能力要跨层迁移,且在新场景下不重新训练就能用。

**为什么是智能问题**：这是**跨本体泛化**——正是智源 RoboBrain-X0（"学习做什么而非怎么动"）、蚂蚁灵波 LingBot-VLA 2.0（20 种构型统一动作表示）在解决的问题。

**对本项目的关键含义**：RoboBrain-X0 的分层（顶层任务意图 → 中间层动作 token → 底层本体控制）**正好对应你的三层指控**。地面显控层做意图,簇首做动作序列,簇内节点做本体执行。**这是可以直接借鉴的架构映射**,不需要重新发明。

**可借鉴的自进化路线**：Zeva 的上下文因果学习（不更新权重）；智谱的完全自训练（需谨慎,离线环境下无法联网迭代）。

## 2. 对已有资料的使用结论

前几轮汇总的资料（16 篇 + 26 篇）中,按对本项目的**可用性**分三类:

### 可直接借鉴的方法（架构层）

| 来源 | 借鉴什么 | 落到哪个问题 |
| --- | --- | --- |
| **PKEG**（Defence Technology, 战术无人机蜂群） | 指令知识图谱 + 原子意图分解 + 结构化校验；**500 条指令分五类（原始/改写/模糊/噪声/复合）的测试方法** | 问题 A |
| **RoboBrain-X0** | "做什么 vs 怎么动"分层；统一动作表征 | 问题 E |
| **Zeva (ICCL)** | 上下文因果学习,零梯度更新 | 问题 C |
| **LingBot-VLA 2.0** | 统一动作表示的 canonical 向量思路 | 问题 E |
| **HERON-World Model** | 多智能体交互预测 | 问题 D（需先实测算力） |

**PKEG 是这批资料里最重要的一篇**——它是唯一真正做战术无人机蜂群指控的,且真机验证过 3 机、20 组飞行、100+ 条指令。其"指令间关系用图结构绑定"的思路,在长指令串上把准确率从 33.5% 拉到 88.2%。

### 明确排除（附理由）

| 排除项 | 理由 |
| --- | --- |
| **Mostik 隐藏状态桥** | 前提冲突：需要两个模型在同一推理栈内共享隐空间,且每 token 传约 2MB 隐藏状态。项目要求**完全离线**,不存在"云端大模型"；且绕过文本会**切断审计链**（项目依赖文本 JSON 提案做 replay） |
| **世界模型机载部署**（LingBot-World 1.3B 等） | 原文的"消费级单卡 GPU"是 GPU,不是 NPU。视频生成类负载在 RK3588 级 NPU 上不可行,需实测 |
| **任何带自主工具调用能力的模型** | **违反项目安全不变式**。`local_model_client.py:64-65` 会对 `tool_calls` 直接抛错；`mission_planner.py:24` 的 `execution_authorized=False` 是硬约束。选型标准中应明确写死：模型不得具备自主工具调用能力 |
| **闭源 Demo 产品**（无权重） | 离线部署无从谈起 |

## 3. 如何度量"智能"——验收指标

**不能用"是否通过 schema 校验"衡量智能**——那是校验器的功劳。建议以下指标:

| 问题 | 指标 | 说明 |
| --- | --- | --- |
| A 语义锚定 | **指代消解准确率**,分五类测试（原始/改写/模糊/噪声/复合） | 直接采用 PKEG 的测试集构造方法 |
| A | **拒绝发明的比例** | 对无法锚定的指令,正确拒绝而非编造坐标 |
| B 欠信息决策 | **决策后悔度**（对比完全信息下的最优解） | 比"是否拒绝"有意义得多 |
| B | **风险相称性** | 高风险任务上的保守度是否显著高于低风险任务 |
| C 失效归因 | **归因准确率** + **重试成功率** | 归因错了重试必然失败,两个指标要一起看 |
| C | **平均恢复步数** | 从失效到有效方案需要几轮 |
| D 语义协同 | **冗余覆盖率 / 视角互补度** | 可量化,不依赖主观判断 |
| E 泛化 | **零样本跨场景/跨机型迁移成功率** | 不重新训练直接换场景 |

**当前 benchmark 的定位**（`benchmark.py`、40 案例）:验证管线正确性,**不作为智能指标**。`DELIVERY_REPORT.md:35` 已明确警告"不得将 scaffold 通过率表述成 LLM 成功率"。这一点应继续坚持。

---

## 4. 建议的推进顺序

**不建议**从问题 E（泛化/自进化）或问题 D（多机语义）起步——它们依赖 A 和 B 打下的基础。

建议顺序:

1. **问题 A（语义锚定）优先。** 它是其他一切的前提:没有从自然语言生成任务的能力,后面的失效归因、多机协同都没有作用对象。且它**直接依赖 Runtime 提供场景数据**,需要尽早发起接口协商（见 `01_runtime_interface_requirements.md`）。
2. **问题 B（欠信息决策）并行。** 它可以在现有 schema 上起步,不阻塞于 Runtime 变更。用现有 fixture 中的 `low_battery`、`uav02_offline` 等未充分利用的案例。
3. **问题 C（失效归因）随后。** 需要 Runtime 提供失败历史。
4. **问题 D、E 视前序成果与算力实测结果决定。** 机载部分必须先完成国产板工具链实测（能否导出、是否支持约束解码）。
