# 待定责：载具能力语义（Vehicle Capability Semantics）

**提出方**：Integration Owner（Runtime / 前端 / 仿真侧）
**日期**：2026-09-29
**请转交**：总体集成负责人
**性质**：**定责请求，不是数据请求。** 本文件不请求任何一方立刻产出数据，
而是请总体集成负责人裁定"这项由谁负责、按什么口径定义"。

---

## 1. 一句话说明这项是什么

算法侧需要"载具能力语义"，**我们的仓库里没有这项数据，且我们判断它不是集成侧能单方面提供的**。

它不是"一张飞机参数表"，而是**让算法能推理"某台飞机是否胜任某个任务"的能力边界声明**。

---

## 2. 具体缺什么（用三个问题说明）

算法侧现在能拿到的每台飞机能力，**只有一个动作枚举列表**：

```json
"capabilities": ["TAKEOFF", "GOTO", "LAND"]
```

它只回答"**能不能做这个动作**"，不回答"**做得到不到位**"。算法因此**无法回答**以下三个问题：

| # | 算法必须回答的问题 | 需要的数据 |
| --- | --- | --- |
| 1 | 这台飞机能飞到那个点**再回来**吗？ | 续航、速度包线、能耗模型。注意是"包线"不是单一数字——不同巡航速度下续航不同 |
| 2 | 它能**拍清**那个目标吗？ | 传感器视场、分辨率、有效距离区间 |
| 3 | 它**适合**干这个吗？ | 载荷清单（相机 / 云台 / 喊话器 / 灯）+ 各自约束 |

算法侧的原话（`algorithm_lab/INTELLIGENCE_HANDOFF/01_runtime_interface_requirements.md`）：

> 当前 `capabilities` 只有 6 个动作枚举（`mission_context.schema.json:135-150`），
> **无法区分"能拍"与"拍得清"**。

---

## 3. 关键：能力语义需要"三态"，不是一张平的参数表

这一节是本文件的核心，也是我们判断**不能只由某一方随便填一张表**的理由。

同一个事实——比如"这台飞机没有相机"——**有三种完全不同的含义，算法必须能区分**：

| 含义 | 算法应当采取的行动 | 需要的标注 |
| --- | --- | --- |
| **暂时未装**（可以申请装载） | 也许应请求装载后再执行 | `conditional` / 附生效条件 |
| **该型装不了**（物理上不可能） | 应改派其它载具 | `unsupported` |
| **不允许使用**（政策 / 授权禁止） | 应放弃该方案或请求授权 | `forbidden` |

**这三者对应的决策完全不同。把它们压成一个"没有"的布尔值，会让算法做出错误的选择。**

### 这个模式在本仓库已有先例

动作注册表**刻意**把两种"做不到"分开，不是随手写的：

- `action_endpoint_not_implemented` —— 能力**尚未实现**（将来会有）
- `action_not_supported` —— 本执行路径**不提供**该能力（例如高风险载荷动作）

转换器（`tools/proposal-to-plan.mjs`）沿用了同一区分，原因写在代码注释里：
措辞不同是为了**避免前者被读成"以后会开放"**。

**因此能力语义建议沿用同一表达方式：带"保证 / 有条件 / 禁止"三态的能力声明，
并附生效条件与来源。**

---

## 4. 现状：数据分散在四个归属不清的地方

我们在集成侧能做的是**查证"我们这侧有没有"**。查证结果如下：

| 需要的数据 | 集成侧有吗 | 我们判断可能归谁 | 依据 |
| --- | --- | --- | --- |
| x500 的**真实**续航 / 速度包线 | ❌ 没有 | 机型 / 采购负责人 | 我们手上没有真机参数 |
| **仿真里**采用什么值、是否代表真机 | ❌ 完全未定义 | 仿真负责人 | `config/three_uav_sitl.json` 只有机型名 |
| 是否装载相机 / 云台 / 载荷，接口是什么 | ❌ 未实现 | 载荷负责人 | `docs/payload_device_adapter_plan.md` 是**计划**，未实现 |
| 谁能规定"允许 / 禁止使用" | ❌ 未与能力关联 | Policy 负责人 | 有 Policy Gate，但只裁决动作，不管能力边界 |

### 集成侧能确认的（仅此而已）

- 仿真机型：`"px4_sim_model": "gz_x500"`，`"airframe_autostart": 4001`
- 三台**完全相同**，`config/three_uav_sitl.json` 中每台只有：
  `node_id / px4_instance / system_id / component_id / gazebo_model_name /
  command_endpoint / telemetry_endpoint / px4_mavlink_local_port /
  gcs_local_port / spawn_ned / runtime_dir`
- **不含**续航、电池容量、最大速度、速度包线、传感器、相机、视场、分辨率、载荷
- 仿真模型自带传感器仅 IMU / 磁力计 / 气压计 / GPS，**没有相机模型**
- `docs/hardware_capability_mapping_template.md` 是一份**空模板**，全部字段为 `TBD`，
  不是已填写的清点

> **重要**：上表最后一条只能说明"**仿真里没有相机**"，
> **不能说明真机有没有**。我们无法从仿真配置推断真机能力，也不应这样做。

## 5. 需要总体集成负责人裁定的四个问题

### Q1 责任归属

上表四类数据，各自由谁负责产出并**签字确认**？

（我们的初步判断是分属机型/采购、仿真、载荷、Policy 四方，
但这只是从文件现状做的推测，**不是我们有权确定的分工**。）

### Q2 仿真值与真机值的关系

仿真里是否必须有这些参数？如果有，**它代表真机还是仅为仿真占位**？
两者不一致时以谁为准？

**我们建议至少要求显式标注来源**，避免"仿真里的默认值"被当成"真机的已知参数"使用。

### Q3 三态语义由谁定义

"保证 / 有条件 / 禁止"的三态区分（第 3 节）应由谁定义？是否需要与 Policy Gate 对齐？

> 这一条与现有动作注册表的 `not_implemented` / `not_supported` 区分是同构的，
> 建议沿用同一套表达，避免两套语义。

### Q4 过渡期怎么办（**这条最急**）

在这些参数确定之前，算法侧**是否允许基于显式假设推进**？

我们的建议：

- **允许**，但要求提案里**显式标注**哪些是假设、假设是什么
- **禁止**把假设值当已知参数写入任何"完成证据"或验收结论
- 涉及安全的决策（如"能否飞到某点再返航"）**不得仅基于假设通过**

**如果这一条不定，算法侧会停在原地**——他们目前无法区分"能拍"与"拍得清"，
因此无法对含感知的任务做出任何有依据的判断。

## 6. 我方（集成侧）能做什么

明确边界，避免被误认为在推诿：

| 能做 | 说明 |
| --- | --- |
| ✅ 把能力语义**接进执行链路** | 场景身份校验、转换器的拒绝语义已经证明这类"执行前核对"是可实现的 |
| ✅ 让 Runtime **在执行前核对**能力声明 | 与 `scene_id` / `map_version` 校验同样的位置与方式 |
| ✅ 在提案与审计里**保留能力来源** | 便于事后判断某个决策基于真机参数还是假设 |
| ✅ 提供**仿真侧的事实** | 机型、句柄、仿真自带传感器——**仅此，且已在上文列全** |
| ❌ 提供真机参数 | 我们没有 |
| ❌ 定义载荷接口 | 不在我们职责内 |
| ❌ 替 Policy 决定什么算"禁止" | 不在我们职责内 |

---

## 7. 不处理会怎样（影响说明）

- 算法侧**无法对任何含感知的任务**做出有依据的判断（他们的核心研究内容之一）
- 若各方各自填默认值，会出现"**提案说能拍到、实际拍不清**"这类**看起来成功**的失败
  ——本仓库已经出现过两次同类问题（位置设定点的 `type_mask` 写错导致飞机不动却零报错；
  收尾误判 `RTL` 为安全悬停导致动作报 `pass` 而飞机在自主返航）
- 这类失败**不会在执行层报错**，因此必须在能力声明阶段就区分清楚
