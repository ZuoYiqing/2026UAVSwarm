# 待定责：载具能力语义（Vehicle Capability Semantics）

**提出方**：Integration Owner（Runtime / 前端 / 仿真侧）
**日期**：2026-09-29
**面向**：总体集成负责人及相关数据负责人
**性质**：定责请求与裁定建议，不是已生效的能力数据契约。下文的职责分配和过渡期规则须由对应负责人确认；本文不要求任何一方立刻填入未经验证的参数。

---

## 1. 一句话说明这项是什么

算法侧需要"载具能力语义"。当前输入提供动作枚举，但仓库里尚无可供算法依赖、带来源与适用范围的载具性能和载荷能力声明；集成侧不能单方面补齐这些事实。

它不是"一张飞机参数表"，而是**让算法能推理"某台飞机是否胜任某个任务"的能力边界声明**。

---

## 2. 具体缺什么（用三个问题说明）

算法侧现在能拿到的每台飞机能力，**只有一个动作枚举列表**：

```json
"capabilities": ["TAKEOFF", "GOTO", "LAND"]
```

它只回答"**能不能做这个动作**"，不回答"**做得到不到位**"。算法因此**无法回答**以下三个问题：

| # | 算法必须回答的问题 | 需要的数据 |
| --- | --- | --- |
| 1 | 这台飞机能飞到那个点**再回来**吗？ | 续航、速度包线、能耗模型。注意是"包线"不是单一数字——不同巡航速度下续航不同 |
| 2 | 它能**拍清**那个目标吗？ | 传感器视场、分辨率、有效距离区间 |
| 3 | 它**适合**干这个吗？ | 载荷清单（相机 / 云台 / 喊话器 / 灯）+ 各自约束 |

算法侧本地草案的表述（`algorithm_lab/INTELLIGENCE_HANDOFF/01_runtime_interface_requirements.md`，当前尚未纳入 Git，仍待算法负责人复核）：

> 当前 `capabilities` 只有 6 个动作枚举（`mission_context.schema.json:135-150`），
> **无法区分"能拍"与"拍得清"**。

---

## 3. 关键：分开描述能力事实、当前配置和使用授权

这一节是本文件的核心，也是我们判断**不能只由某一方随便填一张表**的理由。原稿称"三态"，实际混合了可用性、装载条件和授权。建议分层表达，具体字段和枚举暂不冻结。

以"这台飞机没有相机"为例，至少需要区分：

| 已知情况 | 算法可采取的行动 | 应由谁提供或裁决 |
| --- | --- | --- |
| 已安装、完成必要验证，且满足当前任务条件 | 可进入后续可行性与 Policy 检查 | 机型 / 载荷事实及验证证据 |
| 当前未装，但该机型可装；装载、校准或环境条件尚未满足 | 可提出附条件方案，不得写成当前可执行 | 机型与载荷负责人给出条件和证据 |
| 该机型物理上不支持 | 改派其他载具 | 机型负责人确认 |
| 尚未清点或证据不足 | 标为未知，要求补证；不得推断为支持或不支持 | 数据负责人补证 |
| 载具技术上可用，但当前任务被禁止 | 遵从 Policy 拒绝，不将禁止原因伪装成硬件缺陷 | Policy Gate 按主体、动作、任务与时效裁决 |

前四行描述**能力事实与当前配置**，最后一行描述**动态授权**。同一载具可同时"具备相机"和"本任务禁止拍摄"；不能用单个状态覆盖两者。续航、速度和成像质量也不能只用一个状态替代数值包线，还需单位、测试条件、适用机型/配置、来源、验证时间和不确定性。

### 与现有动作失败码的关系

Runtime 已刻意区分两种**执行端点**结果：

- `action_endpoint_not_implemented` —— 当前执行端点尚未实现；不保证未来一定开放。
- `action_not_supported` —— 本执行路径不提供该动作（例如明确排除的高风险载荷动作）。

转换器 `frontend/swarm-console/simulation-3d/tools/proposal-to-plan.mjs` 沿用了该区分。这说明拒绝原因必须可辨，但**端点是否实现不等于机型是否装得上、拍得清或是否获授权**。载具能力可借鉴"明确区分原因"的原则，不应直接复用这两个失败码作为载具能力枚举。

**建议口径**：能力事实至少区分已验证可用、有条件可用、已证实不支持、未知；Policy 允许或禁止另行裁决。"保证"只在明确的任务条件与证据范围内成立，不能承诺任意任务都成功。

## 4. 现状：数据分散在四个归属不清的地方

我们在集成侧能做的是**查证"我们这侧有没有"**。查证结果如下：

| 需要的数据 | 集成侧有吗 | 我们判断可能归谁 | 依据 |
| --- | --- | --- | --- |
| x500 对应真机的**真实**续航 / 速度包线 | ❌ 没有 | 机型 / 硬件负责人 | 我们手上没有已核实的真机机型与参数对应关系 |
| **仿真里**采用什么值、是否代表真机 | ❌ 当前配置未定义 | 仿真负责人 | `simulation/px4_gazebo/config/three_uav_sitl.json` 有机型和实例配置，但没有经确认的性能包线 |
| 是否装载相机 / 云台 / 载荷，接口是什么 | ❌ 未实现 | 载荷负责人 | `docs/payload_device_adapter_plan.md` 是**计划**，未实现 |
| 谁能规定"允许 / 禁止使用" | ❌ 未与能力关联 | Policy 负责人 | 有 Policy Gate，但只裁决动作，不管能力边界 |

### 集成侧能确认的（仅此而已）

- 仿真机型：`"px4_sim_model": "gz_x500"`，`"airframe_autostart": 4001`
- 三台实例采用同一 `gz_x500` 模型配置；其节点、端口和出生位置各不相同。`simulation/px4_gazebo/config/three_uav_sitl.json` 中每台列出：
  `node_id / px4_instance / system_id / component_id / gazebo_model_name /
  command_endpoint / telemetry_endpoint / px4_mavlink_local_port /
  gcs_local_port / spawn_ned / runtime_dir`
- **不含**续航、电池容量、最大速度、速度包线、传感器、相机、视场、分辨率、载荷
- 当前仓库的三机配置**没有声明相机或成像指标**。实际加载的 PX4/Gazebo 模型及 SDF 可能位于外部 `PX4-Autopilot` 安装目录；仅凭本仓库配置，不能断言其传感器清单或真实成像能力。
- 外部 PX4 模型静态核查（本机 WSL `/home/zyq/PX4-Autopilot`，提交 `171f0f38cf`，2026-09-29）：当前选择的 `gz_x500` 所用 `x500/model.sdf` 引用 `model://x500_base`；`x500_base/model.sdf` 声明了 `air_pressure` / `magnetometer` / `imu` / `navsat`，未声明相机传感器。
- **运行时核查（2026-10-03，修正上一条的依据）**：对运行中的世界查询话题，`x500_0` 上实际存在的传感器为
  `air_pressure_sensor` / `imu_sensor` / `magnetometer_sensor` / `navsat_sensor` /
  `air_speed`（`airspeed_link`）/ `optical_flow`（`flow_link`）/
  `lidar` 与 `lidar_2d_v2`（2D 测距，非成像）/
  **`camera_imu`（位于 `camera_link`，但它是 IMU，不是相机）**。
  **没有任何 `image` 话题。**
  > ⚠️ **依据必须取运行时话题，不能只读 SDF 文件**：静态检查 `x500_base/model.sdf` 时
  > 看不到 `camera_link`，而运行中的世界确实出现了它（上面挂的是 IMU）。
  > 上一条静态结论（"未声明相机传感器"）方向正确，但**单凭读文件不足以支撑它**。
  > 正确表述是：**当前配置装配了可选传感器的挂载位置，但没有装配成像传感器**。
- 同一 PX4 checkout 另有 `x500_mono_cam`（引用 `model://mono_cam`）、`x500_depth`（引用 `model://OakD-Lite`）、`x500_gimbal`（引用 `model://gimbal`）及若干 LiDAR 等传感器变体。它们是**可评估的仿真选型**；切换后还须验证启动兼容性、传感器输出、标定和算法接入，才能声明某项感知任务可用。
  因此当前 `gz_x500` **未装配成像传感器**，不能推断整个 PX4 仿真体系物理上不支持成像；但变体存在也不能证明当前三机已具备成像能力，更不能证明真机能力。
- `docs/hardware_capability_mapping_template.md` 提供字段说明与示例占位行，关键机型和模块信息仍为 `TBD`，不是已填写并验收的硬件清点

> **重要**：当前只能说"**当前配置没有装配成像传感器**"（依据为运行时话题，见上）。
> 是否在本次仿真中装载相机，取决于仿真侧的模型选型；**无论结果如何，都不能据此推断真机能力**。

## 5. 需要总体集成负责人裁定的四个问题

### Q1 责任归属

上表四类数据，各自由谁负责产出并**签字确认**？

（我们的初步判断是分属机型/采购、仿真、载荷、Policy 四方，
但这只是从文件现状做的推测，**不是我们有权确定的分工**。）

### Q2 仿真值与真机值的关系

仿真里是否必须有这些参数？如果有，**它代表真机还是仅为仿真占位**？
两者不一致时以谁为准？

**我们建议至少要求显式标注来源**，避免"仿真里的默认值"被当成"真机的已知参数"使用。

### Q3 能力与授权语义由谁定义

能力事实、装载条件、未知状态和 Policy 禁止分别由谁定义？它们如何在提案、执行前核验与审计中保持可追溯？

> 可沿用现有动作失败码"区分拒绝原因"的原则；不应宣称这些码与机型能力或 Policy 裁决同构。

### Q4 过渡期怎么办（**这条最急**）

在这些参数确定之前，算法侧**是否允许基于显式假设推进**？

我们的建议：

- **允许**，但要求提案里**显式标注**哪些是假设、假设是什么
- **禁止**把假设值当已知参数写入任何"完成证据"或验收结论
- 涉及安全的决策（如"能否飞到某点再返航"）**不得仅基于假设通过**

**如果这一条不定，算法侧仍可做隔离的方案探索，但无法把涉及续航或感知质量的结论作为已验证可执行方案。**

## 6. 总体集成负责人建议裁定（待各数据负责人确认）

本节是供裁定的建议，不代表四方已签字，也不发布新的 Runtime/schema 契约。优先定责任与过渡期边界；字段、枚举、校验接口和验收阈值需在数据与标定证据具备后另行评审。

| 问题 | 建议裁定 | 待确认的交付依据 |
| --- | --- | --- |
| Q1 事实归属 | 指定**机型/硬件负责人**对真机机型、续航与速度包线负责；**载荷负责人**对安装状态、成像/云台性能负责；**仿真负责人**对仿真模型、参数与可观察结果负责；**Policy 负责人**对使用授权负责。总体集成负责人维护跨域映射、来源与版本；算法负责人声明消费条件并提供失败案例。 | 先指定具体责任人，再分别提交资料、实测或仿真证据及签字。任何一方不得替另一方签真机或授权结论。 |
| Q2 仿真与真机 | 两套事实分开管理，明确“仅仿真”或“已验证真机”等来源；不得用仿真默认值填真机能力。若两者不一致，**真机任务以经验证的真机配置与实时状态为准**；仿真验收只证明该仿真条件下的行为。 | 仿真 SDF/启动清单及测试记录；真机手册、安装记录和台架/飞行测量，均注明机型、配置和日期。 |
| Q3 语义归属 | 机型和载荷负责人定义、证实能力事实及生效条件；Policy 负责人定义并裁决授权；总体集成负责人协调可追溯表达；Runtime 负责在执行前按批准后的口径核验。暂不合并为单个“三态”字段。 | 先收集反例：未装但可装、物理不支持、信息未知、技术可用但禁止；再评审数据模型和拒绝原因。 |
| Q4 过渡期 | **允许算法 PoC 使用显式假设**生成研究性提案。每项假设必须标出数值/条件、来源或“无来源”、适用场景和未验证状态；报告分别呈现假设下结果与真实验证结果。涉及返航电量、航程、成像达标等安全或任务完成判断时，未知/假设不能单独使执行检查通过，也不能作为完成证据。 | 算法输出保留假设列表与拒绝/待确认原因；执行许可仍依据实时状态、已验证能力和 Policy。 |

建议的处理顺序：先由总体集成负责人指定 Q1 的具名责任人并明确 Q4 的过渡期边界；随后收集 Q2 的两类证据；最后依据反例和实测结果评审 Q3 的表达与执行核验。坐标标定链路尚未完成，相关能力声明不得暗含已经验证的场景坐标或航程计算。

## 7. 我方（集成侧）能做什么

明确边界，避免被误认为在推诿：

| 能做 | 说明 |
| --- | --- |
| ✅ 设计能力语义如何**接进执行链路** | 可借鉴场景身份校验和转换器的拒绝语义；正式接入仍待责任、证据和接口评审 |
| ✅ 在责任与数据口径获批后设计 Runtime 的**执行前核对** | 可借鉴现有场景身份校验；具体输入、时效和失败码仍需评审，当前尚未实现 |
| ✅ 在提案与审计里**保留能力来源** | 便于事后判断某个决策基于真机参数还是假设 |
| ✅ 提供**已核实的仿真侧事实** | 当前可确认机型名、实例与连接配置；传感器与性能需另查实际模型和运行证据 |
| ❌ 提供真机参数 | 我们没有 |
| ❌ 定义载荷接口 | 不在我们职责内 |
| ❌ 替 Policy 决定什么算"禁止" | 不在我们职责内 |

## 8. 不处理会怎样（影响说明）

- 算法侧可继续隔离实验，但**无法对含感知质量要求的任务**给出经验证的载具适配结论。
- 若各方各自填默认值，会出现"**提案说能拍到、实际拍不清**"这类**看起来成功**的失败
  ——本仓库已经出现过两次同类问题（位置设定点的 `type_mask` 写错导致飞机不动却零报错；
  收尾误判 `RTL` 为安全悬停导致动作报 `pass` 而飞机在自主返航）
- 这类失败**不一定在执行层报错**，因此应在能力声明、执行前检查和结果验收中分别核对
