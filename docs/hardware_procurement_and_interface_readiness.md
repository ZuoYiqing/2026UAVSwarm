# Hardware Procurement and Interface Readiness (for PX4 SITL -> Real Backend Transition)

## 1. 当前硬件路线判断

当前阶段硬件策略应服务于“接口可控 + 可观测 + 可回放”的工程目标，而非整机演示目标。

- 不优先采购封闭整机作为主开发平台；
- 优先开放飞控路线（PX4 / ArduPilot / MAVLink 生态可接入）；
- 优先可挂载伴随计算板的平台（便于部署 runtime / adapter / payload gateway）；
- 优先有可控载荷接口与通信链路的硬件（串口、网口、CAN、PWM、GPIO 等）。

> 当前第一目标是“开放接口闭环验证”，不是“完整飞行展示”。

## 3. 第一批建议采购方向（按优先级）

### P0（先买，支撑接口闭环）
1. 开放飞控开发板（支持 PX4/ArduPilot/MAVLink）；
2. 伴随计算板（可运行 Python runtime、日志、诊断工具）；
3. 遥测/数传链路模块（用于稳定链路验证）；
4. 电源与接口转接板（稳压、隔离、标准化接线）。

### P1（接口扩展）
5. 可控载荷接口模块（串口/网口/CAN/PWM/GPIO 转接）；
6. 调试线缆与安全测试附件（USB-UART、示波/逻辑分析辅助、保险、限流电源、桨叶保护/拆桨工装等）。

### P2（按场景补充）
7. 面向具体业务动作的载荷样件（云台/喊话器/投放器/传感器）——前提是接口开放且资料完整。

---

## 4. 第一批不建议采购内容

- 封闭整机（如接口受限、协议不可控）作为主开发平台；
- 接口不可控的商用一体套装；
- 只能手动遥控、无法程序化接入的设备；
- 无法提供 MAVLink/SDK/串口/网口控制接口的载荷。

---

## 5. 与软件路线的关系（必须对齐）

硬件采购必须直接服务以下链路验证：

`control plane -> policy gate -> adapter gateway -> MAVLink/PX4/载荷接口 -> action_result -> audit/replay`

对齐原则：
- 不改变现有 protocol/policy contract；
- 通过 adapter/backend seam 接入真实硬件接口；
- 保证 action_result 与 audit/replay 的可追溯性。

---

## 6. 风险提醒

1. **接口封闭风险**：设备协议不开放，导致 adapter 无法稳定落地；
2. **算力不足风险**：伴随计算板性能不足影响 runtime/日志/诊断；
3. **通信链路不稳定风险**：丢包/时延抖动影响命令闭环验证；
4. **电源/重量/散热风险**：外挂模块导致供电不稳、热失控或载重超限；
5. **载荷接口不标准风险**：接口电平/协议不一致，联调成本高；
6. **真机安全测试风险**：未建立分级测试和保护措施即进入实飞阶段。

---

## 7. 下一步建议（2~4 周）

### 第 1 周：现有资源清点
- 完成“公司现有资源清点表”；
- 输出可复用资产与关键缺口；
- 确认需补充的接口文档/SDK 列表。

### 第 2 周：开放飞控/伴随计算板选型
- 基于接口开放性、可维护性、供货周期做短名单；
- 定义最小接入拓扑（飞控 + 伴随计算 + 链路 + 基础载荷接口）。

### 第 3 周：采购申请与资料收集
- 提交采购申请（含优先级与替代型号）；
- 并行向供应方收集协议、接线、SDK、示例工程。

### 第 4 周：与 SITL backend 对齐真实接入路线
- 用 readiness diagnostic 对照硬件到货状态；
- 确认“先接口、后动作、再扩展”的接入节奏；
- 锁定第一轮 smoke 条件（不是飞行展示）。

---

## 8. 执行口径

- 工程化表达，避免营销化叙述；
- 不夸大当前能力；
- 第一目标明确为“接口验证”，不是“飞行展示”或“整机效果演示”。
