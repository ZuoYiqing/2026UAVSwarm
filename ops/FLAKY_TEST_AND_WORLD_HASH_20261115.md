## ⚠️ 修正：本文档原先的因果判断有一处是错的

**Runtime 负责人用受控实验推翻了我的推断，他是对的。记在这里，避免以后误引。**

### 我当时说的（错）

> `world_sha256` 每次健康检查都重算 → 冷缓存算得慢 → 超过 1.5 秒窗口 → `not_ready`

### 受控实验证明的（对）

`health.py` 的执行顺序是 **先判遥测新鲜度，后算 ground-reference hash**：

| 注入位置 | 结果 | 说明 |
|---|---|---|
| 在**新鲜度检查之前**注入 1.6 秒 | `not_ready` | **这才是 flaky 的真实路径** |
| 只在 **hash 阶段**注入 1.6 秒 | **仍然 `ready`** | hash 慢**不影响**新鲜度判定 |
| 只在 hash 阶段注入 5.1 秒 | `not_ready` | 但原因是 **5 秒健康信封过期**，遥测仍然是 `fresh` |

**所以：hash 慢不是那个 flake 的原因。**
真实原因是 **fixture 在构建时打时间戳**（`test_three_uav_health.py:110`），
到第 228 行断言时如果已过 1.5 秒 → 遥测 `stale` → `not_ready`。

### 那 hash 缓存还要不要做

**要，但不是为了修 flake。** 它的价值是：

1. **性能**：world 在仿真期间是静态的，没必要每次健康检查读整个 `.sdf` 算两次 sha256
2. **正确性**：仿真负责人这次还加了"采样期间文件变化就撤掉地面证据"的逻辑，这是更强的保证

**教训**：我看到"两件事同时存在"就推断因果，没有验证**执行顺序**。
下次这类判断要去读代码的实际调用顺序，或者像 Runtime 那样做受控注入。

## 机制（读代码得到的，不是猜）

### 三个事实

**① 生产阈值很紧（`simulation/px4_gazebo/health.py:23-24`）**

```python
HEARTBEAT_MAX_AGE_S = 2.5
TELEMETRY_MAX_AGE_S = 1.5      # ← 遥测超过 1.5 秒就判 stale
```

**② 测试 fixture 在"构建时"打时间戳（`test_three_uav_health.py:110-114`）**

```python
now = harness.utc_now()
...
"source_timestamp": now, "valid_for_ms": 5000,
```

**③ `_collect` 里有个冷缓存会慢的 I/O（`ground_reference.py:74-75`）**

```python
raw_digest = hashlib.sha256(world_bytes).hexdigest()
digest = hashlib.sha256(harness.canonical_world_bytes(world_bytes)).hexdigest()
```

### 串起来

```
fixture 打时间戳            ← t0
  ↓
_collect → collect_health
  ↓
读 world .sdf + 算两次 sha256 ← 冷缓存时可能 > 1.5 秒
  ↓
用 now() 算 telemetry_age      ← t1，如果 t1-t0 > 1.5 → status = not_ready
  ↓
assert status == "ready"       ← 挂
```

**第一次跑最慢（import + 冷缓存），所以"第 1 次失败、后面通过"这个模式完全对得上。**

## 问题一：测试用了墙钟，且窗口只有 1.5 秒

**这是测试设计问题。** 现代测试不该依赖墙钟 —— 一旦 host 变慢、磁盘变慢、
或者 CI 上并发跑，就会随机挂。

### 建议修法（三选一，优先级从高到低）

1. **注入可控时钟**（最好）
   `collect_health` 已经有 `clock_probe` 参数，但没有可注入的"当前时间"。
   加一个 `now_provider` 参数，测试传固定时间，完全不依赖墙钟。

2. **fixture 的时间戳在 `collect_health` 内部打**
   把 `_runtime_telemetry(manifest)` 改成传一个 **工厂函数**，
   在 `collect_health` 真正开始评估时才生成时间戳。

3. **最省事但最差**：把测试里的 `valid_for_ms` 调大
   —— 治标，掩盖问题。

---

## 问题二（更重要）：world_sha256 **每次健康检查都重算**

`ground_reference.py` 每次 `collect_health` 都：
1. 读整个 world `.sdf` 文件
2. 算 `raw_digest`
3. 做一次 canonical 变换
4. 再算 `digest`

**而 world 文件在一次仿真期间是静态的** —— 改都不会改。

### 为什么这值得修

| 影响 | 说明 |
|---|---|
| **性能** | 每次健康检查多两次 sha256 + 一次文件读。前端轮询健康/遥测时会被放大 |
| **现场风险** | **`TELEMETRY_MAX_AGE_S = 1.5` 是生产阈值**。weier 上如果恰好撞上冷缓存或磁盘慢，集成健康会翻成 `not_ready` —— 表现为"3/3 在线"偶尔变"离线" |
| **演示观感** | 观众看到"在线节点"忽然从 3 掉到 2 又跳回 3，会以为是系统不稳 |

### 建议修法

**加一层 world hash 缓存**（按 world 路径 + mtime 做 key）：

```python
# 伪代码
@lru_cache(maxsize=8)
def _world_digest(path: str, mtime_ns: int) -> str:
    ...  # 只在文件真的变了才重算
```

**这一改同时修好 flaky 测试和现场风险。**

# 追加（2026-11-15 晚）：Runtime 查出一个**比这个 flake 严重得多**的 bug

> 这条是 Runtime 负责人核实时发现的，与 1.5 秒阈值无关，但**对现场演示影响更大**。

## 现象

双 Runtime 架构（地面 Runtime + UAV-02 机载 Runtime）的**转发层**，
会把一次正常的位姿更新误判成链路断开：

```
机载端组装快照时，前后两次读到的位置必须是同一帧
  ↓
如果中途恰好收到一帧新数据
  ↓
代码为避免"给旧位姿贴上新的时间戳"，把这一帧位姿判为"不可用"   ← 合理
  ↓
但它同时把节点标为「断开」                                    ← ⚠️ 错在这里
  ↓
地面端把该机链路分归零：89 → 0
  ↓
控制台取全队最低分 → 单机跳零会拖低总览
```

## 受控复现结果（Runtime 做的）

> "受控复现中，转发数据未过期、机载原分仍是 **89**，
> 仅因为位置样本更新，地面显示就从 **89 变成 0**。"

**关键区分**：
- **机载原分 89** —— 说明链路本身是好的
- **地面显示 0** —— 转发层的归零逻辑
- **不是"真收不到包"**

## 为什么这是 P0

| 影响 | 说明 |
|---|---|
| **演示观感** | 现场会看到"链路质量 89 → 0 → 89"的跳变，观众会以为系统不稳 |
| **总览被拖低** | 控制台取全队最低分，单机跳零就拖累整体 |
| **误导判断** | 运维会以为是网络问题，实际是转发层逻辑问题 |

## 两个 bug 的性质完全不同

| | 1.5 秒 flake | 转发层误归零 |
|---|---|---|
| 严重性 | 测试不稳定 | **演示级 bug** |
| 影响面 | 跑测试的人 | **现场观众** |
| 修法 | `now_provider`（仿真已做，见 #104） | **把「位姿这一帧不可用」和「链路断开」分开** |
| 状态 | ✅ #104 已修，复测 3/3 通过 | ⏳ **待修** |

## Runtime 的建议（我认为是对的）

> 建议**先不放宽 1.5 秒**。Runtime 侧优先把「位姿这一帧不可用」和「链路断开」分开，
> 继续保留位姿一致性、身份和过期检查。
> **现场验收时同时记录 UAV-02 的机载原分、地面分和各自的 `stale`**，
> 就能分辨是真收不到包，还是转发层误归零。

**最后这句很实用**：现场验收时把两个分数都记下来，出问题能立刻分清是网络还是逻辑。
