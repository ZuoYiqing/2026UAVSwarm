# 三方协商：着陆点证据的信任模型与数据模型

**发起**：集成侧，2026-10-09
**参与**：Simulation（场景与验收）· Runtime（执行前校验）· Algorithm（任务意图与语义）
**当前状态**：PR #88 保持 Draft。本文**只说明问题与选项，不做决定** —— 请三方自行商量。

---

## 0. 为什么现在提这件事

屋顶着陆事故查明之后，Runtime 侧做了正确的收紧：

* `return_home` 不再把"开始收敛"当到达（这个改动**不依赖任何缺失的东西**，可以单独合）
* `land` 增加落点判据：缺站点证据时不报任务成功
* `/api/actions/recent` 按 `action_id` 去重

**方向都对。** 但收紧之后暴露出一个**此前被掩盖的事实**：

> **"这块地可以降落"这件事，系统里没有任何地方能声明。**

在此之前没人需要声明它——因为判据只看 `landed && disarmed`。
现在判据要它了，于是**必须有人回答"谁有权声明、以及系统怎么信他"**。

**这不是 Runtime 单方面能定的**，所以提出来请三方一起看。

---

## 1. 死锁的精确说明

### 1.1 现象

`RETURN_HOME` 会**永久不可用**。不是偶发，是结构性的。

### 1.2 代码依据

**消费端——要求 `validated`：**

```python
# src/uav_runtime/http/routes.py:219（PR #88，f5de832）
if calibration_status != "calibrated" or site_status != "validated" or not calibration:
    return None
# → routes.py:548 拿不到就 execution_admitted=False + landing_site_unavailable，连 RTL 都不发
```

**生产端——永远无法产生 `validated`：**

```python
# src/uav_runtime/http/state_store.py:638-640（PR #88，f5de832）
if evidence["status"] == "validated":
    raise ValueError("trusted_landing_site_producer_unavailable")
public = finite_json({**evidence, "status": "candidate"})   # 就算不抛，也只存成 candidate
```

**加上：`update_landing_site_evidence` 在生产代码里没有调用者**

```
git grep update_landing_site_evidence  -- src/
  → 只有 state_store.py:595 的方法定义本身
  → tests/unit/test_landing_site_guard.py 有调用（测试）
```

### 1.3 结论

```
没有任何路径能产生 validated
  → site_status 只能是 "candidate" / "unavailable"
  → RETURN_HOME 永远被拒
```

### 1.4 这个拒绝**当前是对的**

Runtime 侧的注释说得很准确：

> `The current HTTP bridge has no authenticated Simulation publisher.`
> `A caller-supplied run_id/real_landing flag cannot grant flight authority.`

**任何能访问 `127.0.0.1:8765` 的进程都能调用 HTTP 端点。**
如果那里开一个写入口，就等于让"谁都能宣布"这块地已验证可降落"" ——
而那会直接影响飞行成功判定。

**所以问题不是"拒绝错了"，而是"信任来源还没定"。**

## 2. 一个可能的解法方向（供讨论，不是提案结论）

**不开 HTTP 写入口是对的。但"写入口"不是唯一的可能。**

区别在这里：

| | 谁能写 | 为什么可信 / 不可信 |
| --- | --- | --- |
| ❌ HTTP 端点 | 任何能连 `127.0.0.1:8765` 的人 | **没有任何来源凭证** —— 判据无法区分谁写的 |
| ？ **读仓库的发布者** | 只有能把提交推进仓库的人 | 数据来自**被 review 过的提交**；伪造需要 commit 权限**且**过 review |

**换句话说：信任来源可以从"认证调用方"换成"仓库的提交历史"。**

本项目的惯例一直是这样——标定证据、执行契约、验收报告都是"**进仓库、靠 review**"。

> **⚠️ 这一节只是一个方向，不是结论。** 它需要三方判断：这个换法在你们的威胁模型下
> 够不够、有没有更好或更简单的做法、以及"读仓库的发布者"具体该是什么形态
> （启动时加载？单独的工具？仿真侧已有的发布流程里加一步？）。
>
> **如果三方认为这条路不合适，那就说明白"那 `RETURN_HOME` 在什么条件下才可用"** ——
> 那也是有效的结论。

## 3. 数据模型：一个可能对不齐的地方

这一节是我观察到的一处**可能**的分歧，**不是谁对谁错**。

**Runtime 侧当前实现（PR #88）：**

```
一个字段：status ∈ { "candidate", "validated" }
```

**Algorithm 侧提出的表述（2026-10-09）：**

```
① 静态几何已确认   —— 站点 ID / scene_id / map_version / 中心 / 实际承重碰撞面
                       来自场景配置与 review
② 着陆能力已验证   —— 该机在该站点完成仿真实飞验收
                       附 run_id、场景哈希、软件版本、原始日志引用
③ 当前允许使用     —— Runtime 结合上述证据与实时状态判定
                       不由算法或模型宣布
```

### 3.1 为什么值得讨论

**这三件事的失效条件不一样：**

| | 什么时候失效 |
| --- | --- |
| ① 静态几何 | 场景几何或 `map_version` 改了 |
| ② 着陆能力 | 飞控 / 软件版本变了 |
| ③ 当前允许使用 | 飞机不在站点附近、标定过期……**这是运行时状态，不是证据失效** |

**一个布尔值表达不了这三种不同的失效。**

### 3.2 一个可能的形态（供讨论）

```
存储：① geometry_valid        （场景级，跟 map_version 走）
      ② capability_verified   （每机 × 每站点，跟软件版本走）
计算：③ usable = ① ∧ ② ∧ 实时状态
```

**如果这个形态成立，它的好处是**：③ 变成计算属性而不是存储字段，
于是"谁来授权"这个问题**大半消解** —— 因为没有任何一方需要"宣布可用"，
Runtime 只是把两个已存在的证据与实时状态合起来。

**而且它恰好能表达我们现在的真实状态**：

```
① 几何：已确认（场景配置 + review）
② 能力：**未验证**（逐机真实着陆验收还没做）
③ 结果：not usable —— 而这正是当前应有的结论
```

**单一的 `status` 字段表达不了"几何对但还没飞过"这个中间状态，
而那就是我们此刻的处境。**

> **⚠️ 同样只是供讨论的形态。** 三方可能有更合适的建模方式
> （比如两个字段就够、或者需要第三个维度）。**请以你们的判断为准。**

## 4. 三方分工的一个可能划法

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| **Simulation** | 站点静态几何（含**实际承重面**）、逐机真实着陆验收与原始证据 | 不宣布"可用" |
| **Runtime** | 执行前校验：几何 + 能力 + 实时状态 → 是否放行；失败可见 | 不生产证据 |
| **Algorithm** | 任务意图里引用**已发布的站点 ID** | **不重复实现安全校验** |
| **？** | 授权 —— 见 §1.4 / §2 | |

**Algorithm 侧自己提出的这条边界，我认为值得采纳**：

> 算法只引用已发布的站点 ID，Runtime 负责执行前校验；
> 这部分不应由我们算法线重复实现。

**理由**：两套判据就会有两套失效条件，而它们迟早会漂移。

### 4.1 关于"以后能不能让智能算法来做这件事"

**这个问题我建议留给三方一起想，我不预设答案。** 只说几点观察供参考：

* 当前缺的是**授权**，而授权在工程上通常是**权威问题**，不是**推断问题** ——
  再强的模型也不能替代"谁有权说这块地能落"这个决定。
* 但**有些部分是可能智能化的**，例如：
  - 从场景几何 + 历史着陆遥测里**发现**候选站点与合理容差（而不是人工量）
  - 在多次着陆后**识别**某站点是否稳定可靠（而不是只看一次验收）
  - 在证据缺失或矛盾时**提出**需要澄清的问题（而不是静默放行或静默拒绝）
* **有一条边界我认为应当保守**：无论多智能，**不能由模型"宣布"某站点可用** ——
  那与算法侧自己提的"③ 不由算法或模型宣布"一致。
  能做的更像是**收集与质疑证据**，把结论留给人或确定性判据。

**以上只是观察，不是要求。** 请三方按自己的判断决定要不要、以及怎么把智能能力放进来。

## 5. 不依赖任何决定的、可以现在就做的事

这几件**不需要等上面任何一条定下来**：

| # | 事项 | 归属 | 说明 |
| --- | --- | --- | --- |
| 1 | **把 PR #88 里不依赖站点证据的部分拆出来先合** | Runtime + 集成 | `state_store` 去重、`return_home` 不再把"开始收敛"当到达。**纯收紧、不引入新依赖、不让任何功能不可用** |
| 2 | **把 §1 的死锁写进契约文档并标注为已知限制** | Runtime | 让下一个人一眼看到"现在 `RETURN_HOME` 为什么不可用"，而不是自己再查一遍 |
| 3 | **明确 `landing-pad-UAV-0x` 的实际承重面** | Simulation | world 里它们是半径 1.5 m 的**视觉**圆柱（无 `collision`），承重面是 `ground_plane` 的 z=0。**这决定容差该按什么定** |

**集成侧这边**：独占三机窗口随时可以安排。但要说清**真实联调能验什么**：

* ✅ 可以验：**拒绝行为**（缺证据时确实拒绝）、遥测判据、多机隔离
* ❌ 不能验：**"pad 任务闭环通过"** —— 那需要站点证据到位

**这一点三方应当有共识，避免把"能验的部分"当成了闭环。**
